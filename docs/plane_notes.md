# Parser and Source-Precedence Notes

### Implementation Follow-Up

The original smoke observations below are preserved as the test record. The
current implementation uses in-memory `axon-ext:` archive documents; the URI
hash identifies the archive path, not its contents. Current-file and editable
source precedence, archive replacement cleanup, directory reconciliation, and
dependent diagnostic refresh now have regression coverage. Filesystem recovery
uses bounded retries and remains dependent on VS Code watcher event delivery.

Receiver validation now covers explicit and no-parentheses dot calls. Xeto
parameter defaults are stored separately from types and nullability, including
metadata containing quoted commas and braces. Embedded diagnostic coordinates
and temporal literal types have integration tests. Defaults are not evaluated,
and flow-sensitive type inference and structural conformance remain follow-ups.

### Trap Operator and Reassignment

- `->` is Axon's trap/tag-lookup operator, not assignment. It now has a distinct
  source-spanned AST node and primary/postfix precedence, supporting chains such
  as `rec->siteRef->dis`, `rec->curVal.toStr`, and `inspect(rec->values[0])`.
- Trap keys are literal tag names, not variables or function references. Unknown
  Axon receivers are checked; filter paths retain their tag-name semantics.
  Trap-result types remain unknown, even if a key shares a function's name.
- Incomplete `rec->` expressions preserve the following statement. Regression
  coverage includes call context, Trio/Xeto editor requests, and embedded UTF-16
  diagnostic coordinates. Parser errors are not yet published as diagnostics.
- `:` defines a binding; `=` requires an existing binding. Binding lookup is
  source-ordered and position-aware, including same-line statements, parameters,
  closures, and shadowing. Reassignment does not manufacture a binding or retain
  an initializer's inferred type after mutation.

```axon
rec: readById(@example)
label: rec->siteRef->dis
rec = readById(@replacement) // valid reassignment
absentLocal = 1             // undefined assignment target
```

### Validation — 0.4.3

- `go test ./...` and `go test -race ./...` passed.
- `go vet ./...`, `npm run test:client`, `npm run compile`, and
  `git diff --check` passed.
- Manual VS Code smoke testing passed, as reported by the user.
- Overlapping dot-receiver tests were consolidated without dropping range,
  chain, unknown-signature, or unknown-type assertions. Shared embedded smoke
  fixtures avoid rebuilding the same server/signature index for every case.
- Parser recovery now preserves a following lambda after a multiline Trio
  `src:` field, rather than consuming its opening tokens.

### Remaining Limitations

- Runtime record/tag lookup, structural Xeto conformance, and flow-sensitive
  assignment-result inference are not implemented.
- Some host-format recovery and editor helpers remain line-oriented; the AST
  parser is not a complete compiler or general syntax-diagnostic pass.
- Archive recovery still depends on watcher delivery and bounded retry windows.

## Historical Smoke Record — Resolved Issues

The observations below predate the fixes described above. They are retained as
reproduction context, not as descriptions of the current implementation. The
original archive-content-hash hypothesis was not accurate.

### Function Precedence and Archive Lifecycle

- LSP currently creates a mirrored copy of xetolib files for lookup/file hyperlinking
- It also seems like the filename is generated by some hash of the file contents
- More problematically, the cached file doesn't always appear to update when xeto libraries are built or cleaned


*Example*

Create structure as follows, assume there are non-conflicting external libraries if any

src/xeto
    test.equips
        lib.xeto
        funcs.xeto


1. Initially local editing works fine
2. User runs 'xeto b' which builds the working dir into the test.equips.xetolib archive
3. This archive is now a part of the LSP's overall context, so two issues can crop up
    - When the user goes back to editing test.equips/funcs.xeto it may conflict with the previously built .xetolib archive. That is the foremost problem we were trying to solve, and maybe can be done by giving different LSP sources a 'priority' index or something that helps assign precedence quickly
    - The other problem is that it seems like the LSP, in order to support hyperlinking that source archive, creates a copy of the source files in some "file:///sha1234/test.equips.funcs.xeto" type location. When the spec lib is rebuilt, BECAUSE the file contents change, I'm thinking that the updated library shows up as a new sha location, and the other is not cleaned out. Maybe this was a decision that had to do with progressive/easier loading? NOT SURE!

If the above diagnosis is accurate (needs to be verified still), two fixes need to be put in place:

- A prioritization on function lookup/archiving. Priority always follows:
    - Local functions/workspace in .xeto files
    - .xetolib files cached from within the current workspace
    - .xetolib files cached from user specified external directories in the extension settings
    - The default bundle of specs cached with the LSP


### Dot-Call Receiver Validation

When parsing axon, the following pattern causes issues:

*varName.funcName()* and *varName.funcName* both with and without parens

This is problematic because the LSP fails to recognize that the leading *varName* should be identified either as some value (function or variable)

This can lead to false negatives on syntax hints when a variable is actually undefined, e.g.

```
points: readAll(point)
data: poinTs.hisRead(2026-01-01)
```

In the above example, *poinTs* will not be underlined as an undefined variable. Reviewing the debug output, the LSP appears to recognize an event and calls it as being handled=true, but it's not clear what's causing that parsing issue. Perhaps there is a bad path where the LSP cannot accurately determine the value or type of that variable and so it chooses the safe fail route of assume not enough information to accurately report an error. That indicates we have an issue with Axon syntax parsing.


### Xeto Parameter Defaults and Nullability

Versions of this syntax cause issues for the parser:

```
opts: Dict? <axon:"null">
opts: Dict <axon:"null">
```

This would be in the case where opts is a potentially null/optional argument to a function that might have a signature like:

`foo: { a: Number, b: String, opts: Dict? <axon:"null">, returns: Number}`

The axon meta tag allows the input of a default value, and the ? operator indicates that it could be null or unassigned at invocation.
Currently, the parser cannot make sense of this optional argument syntax, and seems to think it is required.

The parser APPEARS to be reading the type of opts at 'Dict? <axon:"null">' as opposed to just Dict with some internal flag of it being optional/nullable.

**Clarification:** explicit default metadata permits omission independently of
nullability. The current implementation preserves the existing omission behavior
for nullable parameters without explicit defaults; default expressions are not
evaluated to infer or change the declared type.
